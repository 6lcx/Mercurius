找出这次请求哪里出了问题

这是一个故障定位小测试，共 6 题。不用改代码，只需看材料，选出“哪里失败”和“发生了什么”。

先弄懂怎么玩 · 这里不计时

① 找到题目给的编号
编号代表一次用户请求。材料中可能混有其他请求，只看这一条。

② 找第一次失败
后面的重试、切换模型、熔断，可能只是处理失败的后续动作。

③ 选两项并提交
选择失败环节和故障类型；看不出来就选“不确定”，不用猜。

我们想比较：直接看日志与看系统整理的诊断信息，哪种更容易找到问题。两种材料会交替出现。

看一个虚构示例（不计时，不是正式题）

题目：请定位请求 DEMO-001。下面每一行是一件按时间发生的事。

10:00:01　DEMO-002　查商品成功（这是别人的请求，不看它）
10:00:02　DEMO-001　调用 AI 服务，返回 HTTP 429：请求过多
10:00:03　DEMO-001　系统等待后重试
10:00:04　DEMO-001　重试成功
展开示例讲解

失败环节选“AI 模型调用”；故障类型选“限流”。依据是 10:00:02 的 HTTP 429。后面虽然重试成功，但题目问的是最早发生的失败。

如果只看到“已切换备用模型”，却没有说明为什么失败，就不要据此猜原因，可以选“不确定”。

准备好后再进入正式题。每题只有点击“显示材料并开始计时”才开始计时；阅读本页和题间休息不计时。开始后请不要刷新页面，切到其他窗口的时间仍会记录。

看不懂字段或选项？展开中文速查
材料里的文字是什么意思
request_id请求编号，用来区分不同用户请求。
occurred_at / at事件发生的时间。
type / event / payload发生了什么，以及这件事的详细信息。
first_failure / classification系统找到的第一处失败 / 系统判断的故障类别。
model / tool向 AI 服务请求回答 / 调用查商品等业务功能。
rate_limit / 429限流：短时间请求太多，被服务拒绝。
timeout超时：等待超过了允许的时间。
connection_failure连接失败或中断：请求没连上，或传输途中断开。
upstream_unavailable / 503上游服务不可用：被调用的服务暂时无法处理请求。
retry / fallback / circuit重试 / 切换备用方案 / 熔断（暂时停止调用）。这些动作本身不一定是最早的失败原因。

速查只解释词义，不保证材料一定能得出结论；没有足够证据时选“不确定”。
