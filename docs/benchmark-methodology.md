# 简历指标 benchmark：预先登记的方法

制定日期：2026-10-02。目的：独立测量当前工程，而非证明简历里的数字。业务代码在本阶段保持不变；新增内容仅限 benchmark、数据、测试及报告。当前源码无 Git 元数据时，以逐文件 SHA256 作为版本证据。

## 当前可测性与范围

真实入口是 composition.build_container → MainAgentOrchestrator → AgentScope ReAct → FunctionTool → ProductRecommendationService / SQLite 订单及偏好存储。README 中商品 Qdrant/rerank 主链描述已经过时。MainAgent 静态注册 Toolkit；本项目没有业务 ToolSearch/MCP 动态发现实现，因此不能在此测 Haro 的工具描述 Token 减少 85%。

当前设置使用 DeepSeek 兼容 API 和本地 BGE embedding。使用已有项目配置，不输出密钥。全量商业网页搜索与外部商品不是本轮任务集的事实来源：固定种子商品、关闭 Tavily/Redis 语义缓存/队列，运行真实本地 embedding、知识库、SQLite、模型及工具。关闭可选集成不是 mock；这是明确的本地商品实验域，不代表联网购物或生产性能。

1. **任务完成率**：每个 task 的所有预登记机器可验证断言通过且无运行错误，success=1；失败、超时和许可挂起均计0。基线为当前代码移除项目执行保护（工具超时/熔断、Harness、模型重试/回退、轮次重试）；处理组为当前项目保护。不是历史版本复原。现有 eval/cases.yaml 的13类任务，每类3次、每组39任务；记忆写入/读取前置独立设置，修订已过时的商品/材质假定但不按跑测结果挑案例。自动得分称“任务断言通过率”，主观推荐理由/自然程度不假装已人工验收。记录逐条断言和全部输出，人工可复核。成功标准是达到各case契约，不设71%或89%目标。混杂：模型非确定性、权限挂起、任务难度、重复case相关性、共享服务缓存、模型随时间漂移。无故障时两组相同也是有效结果。
2. **Prompt Cache**：主要指标 sum(原始usage缓存命中token)/sum(原始usage输入token)，另报请求命中比例、字段可用率和分窗口统计。采集所有真实模型调用；缺字段是null，不能填0。独立前缀实验：基线将变化偏好放在system开头，处理组使用项目稳定system及独立memory_hint；固定同一组12个买家偏好/问题，每个请求内容重复3次，2组共72次调用，交错组别。第一次仅称first-exposure，无法清空服务端缓存所以不称严格cold。成功条件是得到有效usage与响应；不以处理组获胜为条件。混杂：服务端缓存预热/淘汰、分块、系统及工具schema长度、时间窗口、CriticalFactsMiddleware动态system后缀。独立实验测前缀位置机制，日常Agent usage才是完整流程观测。字段依据：https://api-docs.deepseek.com/guides/kv_cache/ 。不能由一次运行写“长期稳定80%”。
3. **串行/并发**：用相同的三个双品类任务组，通过真实task_dispatch执行；3次重复、2组共18组任务。基线逐个await，处理组gather，保持demands、工具、模型、共享throttle一致。指标墙钟秒、每子任务完成率、事件重叠、paired speedup；不把失败的快速返回当加速。成功条件是两个专家均实际返回可核验工具结果。混杂：模型调用轮数、权限、网关限速、本地embedding锁、缓存及共享状态；并行组不保证更快。不使用不同问题诱导不同执行方式。
4. **上下文压缩**：固定6份购物历史（短/长、预算/商品标识/待确认状态，取真实种子商品工具结果）；每份2次、2组共24次。基线保留完整历史，处理组调用真实Agent.compress_context以及项目CriticalFactsMiddleware。记录压缩前后框架token估计（明确不是服务商计费token）、关键字符串保留率、真实模型探针答案的事实保留率、压缩耗时/额外模型成本。成功条件是预设事实均保留，且无压缩错误；缩减率可以为负。混杂：侧账本/保留消息也占token、摘要随机性、短历史可能膨胀、人工构造历史不同于生产分布。不得仅测摘要长度而忽略system侧账本。
5. **偏好选择与持久化**：实际SQLite存储、PreferenceSelector、orchestrator._build_inputs；12个固定偏好配置（0/少量/大量like与dislike、删除/重启/不同买家），3次、全量基线/当前选择处理组共72行。测选择输入字符/框架token估计、dislike保留率、跨会话读回和删除后权威快照正确性。正向选择效果仅限数量/顺序，不宣称推荐质量提高；语义遵从另由真实Agent任务测试。成功条件是存储与快照契约符合预登记预期。混杂：默认相关性排序关闭、材质资料未知时应澄清而非推荐。
6. **当前检索质量**：完整既有67条product_recall标注、规则基线/规则+真实本地embedding处理组、各3次，共402行；沿用K=8及原relevant，不按结果筛选，分别报lexical/semantic。记录Recall/MRR/NDCG/耗时/硬约束核验及失败。直接测当前ProductRecommendationService，不将旧CatalogSearchUseCase结果称当前线上效果；标签不适配之处单列、不悄悄修标。成功谓词为至少命中一条已标注相关商品，质量主要看完整连续指标。混杂：小种子库、旧标签可能与新硬约束语义冲突、已知样本非held-out、相同文本缓存/CPU热身。
7. **故障恢复/超时/熔断**：真实ThrottledChatModel、ToolResilienceMiddleware与CircuitBreakerRegistry，仅第三方调用边界注入确定故障（第三方API不稳定且收费，不能要求真实服务按计划故障）。包括正常、一次瞬态、持续瞬态、不可重试错误、流前失败、流中失败、超时、熔断恢复；每类10次、保护关闭/开启。报告按故障类别的业务完成、正确失败/不重复输出、调用数、耗时和恢复事件；不混成线上完成率。用于重试的故障计划以逻辑请求为单位相同，不能靠只给基线故障让处理组获胜。缩短等待参数的测试明确标为受控机制实验，不能当默认生产延迟。
8. **可观测性和定位时间**：Agent实际OTel span导出到本地内存并持久化JSONL，业务事件完整保存；报请求ID关联覆盖、有效trace ID覆盖和错误事件。没有人工参与时无法得到“定位30→5分钟”。提供diagnosis start/finish命令记录参与者、随机化问题组、条件、开始/确认根因时间和正确性；不得自动为人填完成时间。建议后续≥12不同故障、≥2人、交叉分组，同一人不能先看答案再计时。本轮人工样本数0，定位时间null，明确不支持旧数字。自动故障检测延迟与人工定位时间分开。

## 执行与统计约定

- 固定seed=20261002，组别配对交错顺序，case及配置在首个计分调用前保存并计算哈希。pilot仅用于验证采集器，不混入正式结果。
- 输出每个run独立目录，manifest含时间、Python/包版本、CPU/OS、数据/业务/benchmark文件哈希、安全配置、计划样本数及实际样本数。绝不保存凭据或Authorization头；只使用合成买家数据。
- 原始results.jsonl逐行flush；真实请求usage另存model_calls.jsonl；事件、span、回答和state存独立artifact。聚合同时输出JSON/CSV/Markdown，可仅依赖原始文件重跑。
- mean/median/P90使用所有已完成观测；超时另计右删失/超时比例，不伪造精确耗时。成功率分母包含失败，字段缺失列出missing。P90采用线性插值，明确样本量；不报告小样本P99。
- 组间比较按case配对，重复运行并非新增独立case。bootstrap按case聚类；区间若包含0则不主张确定提升。没有有效配对时差异null。
- 单任务墙钟上限180秒；每模型调用输出上限4096、temperature=0，底层SDK重试在两组均关闭，项目重试只由实验组控制。真实API调用上限800，达到上限记录未执行而非成功；可显式提高后继续独立运行。失败不自动换模型直到得到漂亮结果。
- 所有业务存储落output/benchmarks/<run>/state，复制/新建实例，不操作现有会话/订单/索引。导入源码和运行正常依赖，不写app/。
- 命令入口拟定：python -m scripts.benchmark.run --suite local|live|all --output ...；python -m scripts.benchmark.aggregate <run>；python -m scripts.benchmark.diagnosis start|finish ...。具体可执行命令随实现文档更新。

## 数字判断规则

80%、71→89、30→5均未预设为目标。只给本次模型/版本/任务集能支持的新数值；没有历史版本、任务集和原记录就不能追认历史改善。模型/权限或产品缺陷导致失败仍是有效测量，应与benchmark程序自身错误区别：后者修复后保留pilot失败记录并重新启动正式run。业务修复应另立版本配对，不在跑测中静默修改。

## Pilot 后的测量修订（正式 live 计分前）

- pilot-v1 暴露采集器没有保留 AsyncStream 的异步上下文协议、构造 Msg.content 类型不符；pilot-v2 暴露压缩历史有 tool_result 却没有配对 tool_call。这些是benchmark自身错误，修正后重跑pilot，旧记录保留但不计正式结果。
- pilot-v2 证实当前 product_search_tool 的 ToolCallBlock.state=asking，最终回复等待许可，未执行工具。这是当前业务接线结果，不改源码、不隐藏失败。正式 default 组保留该行为。
- 增设独立的 --consent-product-search 补充实验：仅在benchmark构建Agent时添加该工具allow规则，关闭第三方网页搜索且使用隔离目录；代表已获得工具执行授权的测试环境。另一个输出目录、显式manifest/逐行标识，不能与默认组混算，不能当作项目已修复。此组沿用相同case与评分，观察权限条件满足后的行为。
- 压缩实验控制模型context_size以实际触发框架压缩，但请求仍发往同一真实模型；计入system关键事实侧账本，明确是受控窗口实验。
- 机器评分只覆盖可验证的最小任务契约，不等于原rubric全部自然语言要求；报告使用“任务断言通过率”，不称完整用户满意度或线上完成率。
- 补充上下文隔离实验（在其首个计分调用前登记）：从真实商品结果构造6份历史，覆盖无干扰、无关品类及已撤回旧约束；同一检索需求/当前约束，baseline继承历史、treatment新建空上下文；各2次共24任务。直接使用项目SearchAgentFactory，补充环境预授权本地商品搜索。记录真实input_tokens、最终回答与工具证据中目标商品/预算是否满足；任务成功要求最终也引用目标商品。不根据输出更改历史或目标。包含无干扰条件以避免先验偏袒隔离组。该实验不代表主Agent自动派发决策的准确性。
- 授权补充实验开始前加强并发计分：必须每个专家输出都含非空JSON hits且ID能回溯真实工具结果，不能仅凭组内出现两次搜索就判两个子任务完成。原配置并发全部挂起，已有原始输出保留；报告时对原配置输出也用此更严格条件复核，不会把失败变通过。
- live-consented-v1 因“速干毛巾”简短查询无商品导致压缩历史夹具无法构建而中止，保留为未完成运行，不混入正式结果。压缩夹具修正为预先指定的六商品P1008/P1001/P1004/P1005/P1010/P1007，用它们的完整目录标题调用当前推荐服务，并在首个模型调用前验证全部六份结果。此更改只保障有真实工具事实可压缩，不改任何Recall标注、Agent任务或成功阈值。重新完整运行授权补充v2，不挑保留v1通过项。
- v2预检在任何模型调用前发现：完整标题查询也不保证其来源商品排名第一。压缩实验不评搜索排名，因此v3保留同样六个查询，使用服务实际首条返回的商品事实构造历史；记录查询来源ID与实际返回ID，全部验证非空后再付费调用。事实保留的成功条件不变，检索评测完全不变。v1/v2继续保留为未完成运行，v3从头完整运行，不拼接通过项。
- v3观测发现评分器将154与154.0等价金额当成不同字符串。修复金额数值等价校验，保留原始results.jsonl和回答，用rescore命令统一复核所有Agent样本（包括默认组），单独保存新旧评分、证据哈希和评分器源码。只纠正表示格式，不改变目标金额、任务输入或其他成功条件；聚合使用复核分数并公开修正数量。不会重新调用模型选更好的回答。
