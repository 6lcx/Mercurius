# 面试案例：HTTP 200 掩盖的向量建库失败

记录日期：2026-09-16。依据：用户提供的网关故障与评测局限截图、当前项目代码与已有评测记录。用途：回答项目重点难点、踩坑及解决过程。

## 可直接讲述的版本

项目里一个比较隐蔽的坑，是商品检索服务看起来正常，但向量检索已经失效了。

当时为了让召回评测有区分度，我们把商品种子库从 10 个 SPU 扩到 60 个。扩容后向量建库失败，日志只给出 JSONDecodeError，服务仍然能返回商品，因为系统自动降级到了关键词召回。只看接口是否成功，很容易漏掉这个问题。

排查时，我把问题缩小到 embedding 网关的批量请求，逐步改变输入条数，同时检查状态码、响应头和实际响应体长度。历史探测记录中，2、8、10 条能正常返回，16、60 条却返回 HTTP 200、JSON 类型的响应头和空 body。项目最终按该网关单批 10 条的限制处理。原来的种子库恰好只有 10 条，因此一直没触发这个边界。

修复放在 embedding 客户端：按可配置的批量上限切片，默认每批 10 条，串行请求后拼接结果；每片按返回的 index 恢复顺序，避免商品与向量错配。同时在 JSON 解析前检查空 body，给出包含批量大小和配置项的明确错误，避免只留下难以定位的 JSONDecodeError。

最后用 6 条回归测试覆盖分片、顺序、空输入和异常响应。项目已有的召回评测也说明这个问题为什么重要：在当时 12 条语义查询上，向量检索的平均 Recall@8 为 1.000，关键词检索只有 0.361。服务可用不代表检索质量正常，降级必须能被观察到，测试数据也要覆盖超过单批限制的规模。

## 重点难点与排查逻辑

| 环节 | 关键点 |
|---|---|
| 为什么扩库 | 只有 10 个商品时，如果 Top-10 覆盖全库，Recall@10 容易饱和，无法有效区分检索策略。扩到 60 个后才能暴露规模与排序问题。 |
| 为什么难定位 | HTTP 200 通过状态码检查，响应头又声明 JSON，实际却没有内容；异常发生在 JSON 解析阶段，表象与批量约束不直接对应。 |
| 为什么难发现 | 建库异常被捕获后降级，主流程继续工作；字面检索表现尚可，语义检索的损失更明显。 |
| 如何缩小范围 | 控制输入条数，比较响应状态、类型、长度，定位到批量请求与网关行为的关系。截图仅展示 10 条成功、16 条失败，不能单凭这些采样严格证明 11 条就是失败边界。 |
| 如何修复 | 默认 10 条分片串行请求，可通过 EMBEDDING_MAX_BATCH 调整；分片内按 index 排序，分片间按输入顺序拼接。 |
| 如何防回归 | 用模拟 HTTP 响应验证批量大小、结果顺序和可操作的异常信息；用按查询类型分组的召回评测发现质量退化。 |

## 已核实的实现与验证

- `app/infrastructure/embedding/openai_embedding_client.py`：已实现分片、空输入直接返回、空 body 检查、缺失 data 检查、按 index 排序。
- `app/infrastructure/vector/index_bootstrap.py`：建库失败时记录 warning 并降级。因此准确表述是“业务仍可响应，仅留下警告，质量退化容易被忽略”，不能说完全没有日志。
- `app/application/usecases/catalog_search.py`：返回 recall_strategy，可辨别实际召回策略。指标监控与自动告警属于可继续完善的措施，不能说本次已经完成。
- `tests/test_embedding_client.py`：6 条测试覆盖 60 条拆成 6 批、乱序与跨片顺序、空输入、空 body、缺失 data、HTTP 错误。2026-09-16 本地运行结果：6 passed。
- `eval/product_recall.jsonl`：67 条标注，55 条字面类、12 条语义类。
- `docs/教程实现对齐清单.md`：“真实跑测结果”记录历史 K=8 对比；本次没有重跑远程网关或真实召回评测。

## 面试追问的回答边界

**为什么不直接重试？** 如果是确定的批量超限，原样重试通常仍然失败，应先满足请求大小约束。瞬时网络故障的重试属于另一类问题。

**为什么使用串行分片？** 先以较简单的方式保证请求大小和返回顺序可控。串行不是满足单批限制的唯一方案；后续可根据吞吐需求和网关并发限制采用有界并发，但该案例未验证其收益。

**空 body 就一定是批量超限吗？** 不一定。这是本案例结合批量探测得到的判断，因此当前错误消息写的是“通常是”，不能把它当作所有网关的通用规律。

**为什么必须检查顺序？** 向量要与输入商品一一对应。即使数量正确，顺序错误也会把 A 商品的向量绑定给 B 商品，造成无异常但结果错误。

**效果提升了多少？** 可以引用历史策略对比：语义子集平均 Recall@8 为 1.000 对 0.361，相差 0.639，即 63.9 个百分点。它不是本次重新测得的修复前后实验，也不是全体查询的下降幅度。整体 Recall@8 的历史对比是 0.978 对 0.871。

**是否证明 rerank 有效？** 不能。历史记录说明未配置 RERANKER_BASE_URL，embedding_rerank 与 embedding_only 的结果相同，不能据此声称验证了重排收益。

**是不是生产事故？** 现有证据支持这是扩库与召回评测暴露的问题。没有额外证据时，不要描述为真实生产事故、用户投诉或线上损失。

以上第一人称讲述稿应按本人实际参与情况调整：亲自完成的步骤用“我”，团队完成或复盘学习的部分如实说明。

## 延伸案例：如何判断召回评测是否可信

这部分对应“这套评测的真实局限”截图，已根据实际代码核对。它可以用于回答“项目还有哪些不足”“如何证明优化有效”“为什么不直接换更强的模型”。

### 1. 语料规模与构造方式限制了结论范围

`scripts/eval/run_product_recall.py` 的 `build_usecase()` 使用 `InMemoryProductRepository()`，默认加载 `build_seed_products()`。本次实际统计为 60 个 SPU；评测并不自动覆盖项目中所有外部商品或运行时新增商品。

除了数量小，语料还有人工构造偏向：`seed_products.py` 明确写出中文标题与关键词化描述便于命中；新增语料还刻意避免与既有 P1001 的测试查询正面竞争，以保持原有 Top-1 断言。因此它适合验证已覆盖场景和诊断检索差异，但并不是从真实用户请求中独立抽样出的代表性测试集。

截图中“可靠回答改动有没有让召回变坏”需要限定为“在这套固定语料和标注覆盖的场景下”。目前门禁甚至没有比较历史基线：某次 Recall 从 0.98 降到 0.80，只要其他指标达标，仍会 PASS。发现这种退化需要主动比较两次结果，不能依赖当前绝对阈值自动识别。

后续改进可包括扩大商品库、增加同品类难区分商品与真实查询、保留独立测试集，并固定商品快照、标注版本及模型配置。上述措施是建议，尚未由当前评测脚本完整实现。

### 2. 阈值是最低护栏，而且目前只作用于总体指标

`scripts/eval/metrics.py` 的 `Thresholds` 与 `gate()` 实际规则如下；命令行可覆盖默认值。

| 条件 | 结果 | 商品评测脚本退出行为 |
|---|---|---|
| 标注集为空 | BLOCK | 非零退出 |
| Recall < 0.75 或 MRR < 0.65 | BLOCK | 非零退出 |
| NDCG < 0.70，且无上述阻断 | WARN | 不因该项非零退出 |
| 均未触发 | PASS | 正常结束 |

代码中没有统计校准、置信区间或与历史基线比较的逻辑。这些值是可配置的经验下限，不能作为“达到优秀水平”或“没有退化”的证明。脚本支持通过退出码接入 CI，但这不等于已经部署了自动发版门禁。

更容易被忽略的是：`by_kind()` 虽然分别计算字面类和语义类结果，但 `main()` 与 `render_report()` 调用 `gate()` 时传的是每个策略的总体 `Aggregate`，没有对语义子集单独设门禁。`filter_accuracy` 也不参与 `gate()` 判定。

这是代码层面可以推出的风险：55 条字面查询全部满分、12 条语义查询全部零分时，总体宏平均仍有 55/67 ≈ 0.821。如果 Recall、MRR、NDCG 都满足这一分布，三个总体阈值都能通过，语义能力却已完全失效。这是假设示例，不是实际跑测结果。

改进方向：保留总体下限，增加语义子集门禁、相对基线退化检查，并明确硬约束失败是否应阻断；阈值需结合扩充后的样本和业务容忍度重新校准。

### 3. 标注自检不能替代标注一致性检验

本次检查 `eval/product_recall.jsonl`，共 67 条，字段包含 query、kind、relevant、note 及可选约束，没有第二位标注者、独立判定或争议仲裁记录。项目已有文档说明为单人标注；“单人完成”来自历史记录，不能仅凭 JSON 字段倒推出标注人数。

`validate_datasets.py` 会检查相关项非空、重复 ID、商品存在性、kind 合法性，以及部分价格和配送约束自洽。本次商品 67 条、品类 22 条均自检通过。这证明标注通过了这些规则，不能证明“颈枕查询是否应把含颈枕的套装算相关”等主观判断一致，也不能证明相关商品已标全。

顺序也属于标注的一部分：`ndcg_at_k()` 把 relevant 列表第 i 项赋予 `len(relevant)-i` 的线性 gain，没有独立的相关性等级字段。因此相关商品排在标注列表的哪里，会直接影响 NDCG；“应不应该相关”与“谁更相关”都需要明确规则。

后续可先统一商品/套装、属性、预算等判定规则，再让两人对同一批 query-product 对独立标注、记录分歧并仲裁。若计算 Cohen's kappa，需要双方对共同判断单元给出类别标签，不能直接对两份长度不同的 relevant 列表套公式；排序分歧也应另行核对。当前没有实现这套流程。

### 4. 12 条语义查询有诊断价值，但不足以支持稳健选型

实际统计为 55 条 lexical、12 条 semantic。`evaluate()` 对查询做等权宏平均，因此语义子集里一条查询的 Recall 从 0 变到 1，就会使该组平均值改变约 1/12 = 0.0833，即 8.33 个百分点。样本少时，少数查询就能明显改变均值。

历史记录中，语义 Recall@8 为向量 1.000、关键词 0.361；字面类则为向量 0.973、关键词 0.982。这支持“在当前样本上，两种策略呈现不同强项”，不能推导出所有真实业务请求上的收益，也没有统计检验证明这点字面类差异稳定存在。

“扩到至少 50 条”应作为项目下一步的样本扩充目标，而非统计充分性的通用门槛。需要覆盖不同品类、表达方式、模糊意图和难例；后续可在同一批查询上比较逐条差值、估计不确定性，并保留未参与调参的测试集。当前脚本没有置信区间、显著性检验或调参集/测试集划分。

### 5. 当前是降级链路，还没有 Hybrid / RRF

`CatalogSearchUseCase.execute()` 优先向量召回，再尝试 rerank；向量异常或候选为空时走关键词兜底。向量成功且有候选时，不会同时调用关键词召回并合并结果。

`_keyword_recall()` 对全库遍历，`tokenize()` 使用空格切词与中文 2-gram，`_keyword_score()` 计算共有词项数量并在品类匹配时加分。它不是 BM25：没有 IDF 或文档长度归一化。在当前商品检索链路和评测脚本中，也没有 RRF 融合实现。

因此不能把项目描述为“已经实现 BM25 + 向量混合检索”。已有结果只是提出了值得验证的假设：两路候选可能互补。不能在未实验前承诺 Hybrid 一定提升；融合也可能把不相关商品推到前面。

可行的后续实验是加入 BM25，与向量分别召回，在 product_id 层去重，再按两路排名做 RRF，之后按需重排。固定数据集、输出 K，明确各方案的候选数量及成本预算，对比单路、融合和融合后重排的分组指标，同时记录延迟与调用成本。当前脚手架可以复用指标与数据集，但需要新增策略装配和报告信息，不能认为已经覆盖了这些实验。

### 代码核对额外发现的评测盲点

**报告中的目标档位不保证就是实际执行档位。** UseCase 返回 recall_strategy 和 rerank_applied，但 `run_dataset()` 没有将它们保存到 `QueryResult`。`build_usecase()` 对失败/缺少配置打印警告后，仍返回请求的 strategy；`main()` 取到的 actual 也没有使用，并按请求策略给报告命名。于是“embedding_rerank”一栏可能实际没有重排，部分查询也可能已走关键词。改进应记录逐条实际策略、汇总降级比例，并在要求严格对比时拒绝把降级结果当作目标策略的测量值。

**候选深度与过滤位置会影响解释。** 向量召回固定 `_RECALL_TOP_N = 8`，硬约束过滤发生在召回之后，被过滤后没有补召回；关键词则对全库匹配项打分后再过滤。默认评测 K=8 能避免 K>8 对向量候选上限的额外偏差，但不代表两路候选预算和过滤覆盖完全相同。此处测量的是当前完整检索流程的表现，不能把所有差异都归因于 embedding 模型本身。

**“过滤准确率”只覆盖部分检查。** `check_filter()` 检查配送不支持的商品是否进入 hits，以及标注相关项是否出现在 filtered_out；它没有独立校验返回商品是否超预算，且 UseCase 的 filtered_out 摘要最多保留 3 条，后续误杀可能不在摘要中。因而历史“过滤准确率 1.000”只代表这些有限检查通过，不能当作全部硬约束正确的证明。

**这是模块评测，不是用户体验全链路评测。** 脚本直接把 query 填进 `ProductSearchSpec.normalized_query` 并调用 UseCase，绕过 HTTP、Agent 和自然语言约束提取；也没有测量吞吐、延迟或调用成本。它不能单独证明端到端回答质量或大规模服务能力。

### 可直接讲述的面试版本

做完商品召回评测后，我特别关注的是指标能证明什么。当前只有 60 个商品、67 条人工查询，其中语义查询只有 12 条，所以它适合做已覆盖场景的回归检查，不能直接拿来宣称某个模型在真实大库上更优。

代码核对时还发现，虽然报告按字面和语义类型拆分了指标，门禁却只检查总体均值。字面查询占了大多数，可能掩盖语义能力的明显退化。另外，系统会自动降级，但评测没有保存每条查询实际使用的策略，报告名称不一定等于真正测到的链路。

已经实现的是指标计算、分组报告、标注自检和可配置的绝对阈值。下一步应先补实际策略记录和语义子集门禁，再扩大并复核标注、加入独立测试集及基线比较；之后用同一套评测验证 BM25 与向量融合是否有收益。这个项目让我认识到，评测本身也需要验证：通过阈值不等于没有退化，一个高分也不等于结论可以推广。

这里“发现并分析评测盲点”已完成；新增门禁、多人标注、扩大样本和 Hybrid 改造仍是后续方案，面试时应明确区分。

## 延伸案例：LoopDetector 的软提示、误判与接入覆盖

核对日期：2026-09-17。截图中“在碰到硬上限之前提示收敛”的设计与检测器实现基本一致，但商品搜索示例需要修正：当前工厂装配没有给商品搜索工具挂载 HarnessToolMiddleware，不能据此声称真实商品搜索连续三次已经会触发提示。

### 它解决什么问题，具体如何工作

`max_iters` 限制 Agent 迭代次数，但不会主动判断中间的工具调用是否重复。`app/application/harness/loop_detector.py` 实现的是成本较低的重复调用启发式：按 shopping_session_id 分桶，保存最近的工具名称序列，默认窗口 6、连续次数阈值 3。阈值由 `LOOP_REPEAT_THRESHOLD` 配置，默认值来自 settings；当前装配没有另外配置窗口。

`check(session_id, tool_name)` 先记录本次工具名，再从序列尾部向前统计同名工具连续出现次数；达到阈值就返回收敛提示。它没有接收工具参数或结果，因此不能判断需求是否更明确、有没有新增候选、任务是否推进。

| 被检测器观察到的调用序列 | 默认行为 | 应如何解读 |
|---|---|---|
| A、A | 无提示 | 未达到 3 次阈值 |
| A、A、A | 第 3 次提示 | 检测到连续同名调用，不代表已经证实无进展 |
| A、B、A、B、A、B | 不提示 | 统计的是尾部连续重复，不是窗口内总次数，也检测不到这种交替循环 |
| A、A、A，但每次参数不同 | 第 3 次仍提示 | 参数不参与判断，可能提示到正常的逐步细化 |
| 会话甲 A、A；会话乙 A | 乙不提示 | 会话之间的记录隔离 |

连续调用超过阈值后，每次仍可能提示，没有“只提示一次”的冷却逻辑；默认窗口最多记 6 次，所以长串重复的显示计数会封顶在 6。若将阈值设得大于窗口，则永远达不到阈值；当前实现没有校验这两个参数的关系。

### 提示注入不等于阻止工具执行

`app/infrastructure/harness_middleware.py` 的执行顺序是：先做顺序准入检查，未被拒绝才运行 LoopDetector，然后仍调用 `next_handler(**input_kwargs)` 执行工具。工具产生结果后，中间件将收敛提示以 `[harness]` 前缀追加到最后一个结果 chunk。

因此第 3 次调用已经执行了，提示主要影响模型后续决策，并没有省掉当前调用，也没有强制终止 Agent。顺序准入检查能够拒绝某些写操作，这是另一个护栏的行为，不能算作 LoopDetector 的能力。

触发时会记录日志，并在有 event bus 时发布带 `harness: loop_detected` 的 `tool.result` 事件。但是事件在工具执行前就发布，提示在工具结果返回后才注入；若下游没有返回 chunk，中间件直接结束，模型可能拿不到提示。因此事件次数既不等于提示实际送达次数，也不等于成功阻止循环次数。

当前提示文案包含“但仍未推进”，比检测器掌握的证据更强。代码只观察到工具名重复，更准确的未来文案应是“检测到连续调用，请检查是否获得新信息；如果正在细化条件，可继续合理检索”。这里记录的是改进建议，本次没有改动代码文案。

### 截图中的背包示例：规则成立，但当前商品搜索没有接入

假设商品搜索工具已挂载 Harness，连续搜索“旅行背包”“35L 旅行背包”“35L 可折叠旅行背包”时，虽然参数不断细化，三次工具名都是 `product_search_tool`，检测器仍会在第 3 次产生提示。模型应结合新条件和新结果决定是否继续，不应机械停止。若参数与结果都重复，则更适合告知暂无新增候选、调整条件或澄清需求。

但当前装配实际是：

- `MainAgentFactory._resilience()` 在 `harness_enabled` 为真时添加 Harness，再添加 ToolResilience；它用于主 Agent 显式构造的任务派发工具、偏好记录工具与偏好撤回工具。
- 商品搜索和品类工具由 `SearchAgentFactory.build_tools()` 创建；该工厂的 `_resilience()` 只有 ToolResilienceMiddleware。
- 主 Agent 通过展开 `self._search_factory.build_tools()` 复用这些工具，没有再套一层 Harness；SearchAgent 自己使用的也是这套工具。
- 主 Agent 的 TaskCreate/TaskUpdate/TaskList/TaskGet 也未在此处显式挂 Harness。所以检测器观察到的是“经过该中间件的调用序列”，并非完整工具轨迹；未被观察的调用也不会打断它记录中的同名连续序列。

结论：当前商品搜索既有超时/熔断保护，但没有通过这条装配获得 LoopDetector 提示。截图示例可以用于解释算法误判，不能用于证明实际产品链路行为。任务派发层面的提示也不能替代对子 Agent 内部每次商品搜索的检测。

### 会话隔离与硬边界

`composition.py` 创建共享 LoopDetector，注入 MainAgentFactory 和 MainAgentOrchestrator；检测器内部按会话 ID 保存状态。Orchestrator 的轮末 finally 路径调用 `reset(session_id)`，设计上避免上一轮正常搜索影响下一轮。这个 reset 位于会话持久化和对话记录之后；不能仅凭它位于 finally 就声称前面的清理动作异常时也必然执行。

当前主 Agent 配置 `ReActConfig(max_iters=15)`，SearchAgent 和 TradeAgent 为 6。这是各 Agent 的迭代边界，不能直接等同于全请求最多 15 次工具调用或全系统总调用上限。

项目另有请求级 TokenBudget，由 orchestrator 初始化，`TOKEN_BUDGET_TOTAL` 默认 0 表示关闭。因此面试时应表述为“软提示之外还有迭代上限；预算护栏需要配置启用”，不能声称预算默认就在限制所有请求，也不能说 LoopDetector 自己负责硬停止。

### 已验证什么，尚缺什么

本次运行 `tests/test_harness_guards.py` 与 `tests/test_harness_middleware.py`，共 43 条测试通过；其中 LoopDetector 专项 5 条，覆盖阈值前无提示、第 3 次提示、交替工具不触发、会话隔离和 reset。中间件另有一条测试，手动给名为 product_search_tool 的 FunctionTool 挂 Harness，验证结果出现提示。

这证明检测器规则和手动接入后的提示注入可用，不能证明真实工厂已接入，更没有验证模型看到提示后会怎样行动。43 条也不是 43 条 LoopDetector 专项测试，其余包含其他 Harness 护栏测试。

后续验证建议分三层：先测试真实 Main/Search 工厂构造出的工具中间件，确认覆盖范围；再使用不同参数与结果的调用轨迹检验误报、漏报；最后观察模型收到提示后是否仍重复、是否合理继续检索或结束任务，以及任务成功率和成本变化。不能把 loop_detected 事件直接当作“成功阻止死循环”的业务指标。

若要增强检测，可结合规范化参数、结果摘要或新增候选数量，区分完全重复与正常细化，并识别 A/B 交替调用；但这些属于后续方案，当前只按工具名检测。

### 可直接讲述的面试版本

项目里对 Agent 循环控制做了两层考虑：迭代上限负责限制运行轮次，LoopDetector 希望在重复调用时提前提示模型调整动作。它按会话保存最近工具名，同一工具连续三次就给收敛提示，但不会阻止当前工具执行。

这个设计的难点是不能把重复调用直接当成没有进展。例如连续搜索背包、35L 背包、可折叠背包，实际上可能是在细化需求。当前检测器不看参数与结果，所以既可能误报，也抓不到两个工具交替打转；提示触发只能作为检查信号，不能直接算作成功防止死循环。

核对实际装配时还发现，检测器和中间件测试虽然通过，商品搜索工厂却只挂了超时与熔断中间件，没有挂 Harness。它说明模块测试通过不等于功能已经覆盖业务入口。后续应先补齐并验证实际接入，再根据参数、结果和提示后的行为评估效果。当前完成的是实现分析和缺口定位，尚未修复这处装配或验证模型收敛收益。

## 延伸案例：主 AgentLoop 的编排、可靠性与状态管理

核对日期：2026-09-17。对应“本章小结”截图。以下将架构机制、已验证行为和仍需验证的效果分开，适合回答“为什么采用多 Agent”“怎么保证不会失控”“如何支持多轮会话”。

### 1. 主 Agent 具备直接执行能力，派发是可选路径

`MainAgentFactory.build()` 的工具集可以归为四层：

| 层次 | 代码中的工具 | 设计目的 |
|---|---|---|
| 业务工具 | Search/Trade 工厂的 build_tools() 返回的工具 | 主 Agent 可以直接检索、处理订单，简单任务无需绕经子 Agent |
| 计划工具 | TaskCreate、TaskUpdate、TaskList、TaskGet | 记录与更新任务计划，不等于任务已经被执行 |
| 派发工具 | task_dispatch | 用 FunctionTool 包装新建子 Agent 的执行过程 |
| 记忆工具 | remember_preference_tool、forget_preference_tool | 保存和撤回长期偏好 |

“与子 Agent 同一批工具”准确说是复用相同工厂构造逻辑，不是所有 Agent 共用同一个 FunctionTool 对象。`globex.yml` 同时规定默认直接调用业务工具，仅在子任务可独立并行、需要隔离中间上下文或调用链较深时派发。代码提供选择空间，提示词引导何时选择；有工具能力并不保证模型每次都选对路径。

面试可解释为：不为了多 Agent 而强制多 Agent。简单查询直接执行，减少额外模型调用和上下文转述；复杂子任务才使用独立工作上下文。这是设计目标，本次没有测量这种策略的成本收益。

### 2. 并发开关、模型行为与实测证据是三件事

`task_dispatch` 在主 Agent 中注册为 `is_concurrency_safe=True`，提示词及工具说明要求独立子任务同轮发起。核对当前安装的 AgentScope 源码，框架会按并发属性分组，并使用 `asyncio.gather` 执行并发批次。因此同轮产生多个合适的工具调用时，存在真正并发执行的代码路径。

但这个属性不会自动判断业务依赖，也不会强迫模型同轮派发；模型仍可能逐个调用。网关并发限制、共享资源竞争和子任务长短差异也会影响实际耗时。尤其不能因为 task_dispatch 被标为可并发，就认为所有交易子任务都可以安全并行。

`scripts/verify_parallel.py` 提供两类观测：串行/并行提示下的请求总耗时，以及派发完成事件中的 started_at/finished_at 区间重叠。`task_dispatch_tool.py` 使用时间戳标记区间，使用 monotonic 计算 elapsed_ms。

解读时需要注意：区间重叠证明派发任务生命周期存在重叠，不直接证明底层每次模型调用都重叠；一次串并行对比也不是稳定的性能基准。该脚本每种模式各跑一次，没有保证模型实际完成相同数量、相同质量的工作，也没有自动强制串行版零重叠、并行版恰好三次成功派发。稳健评估应检查轨迹与结果可比性，并重复测量耗时和成本。

另外，韧性中间件也会为 task_dispatch 发布不含 agent/started_at/finished_at 的失败事件，而脚本 `_dispatch_intervals()` 对同名 tool.result 直接访问这些字段；遇到这类事件可能 KeyError。子 Agent 执行异常时，工具自身也不会发布正常完成区间。当前脚本适用于成功路径验证，不能把失败或缺失的区间当作并发不存在。本次未运行需要服务和真实模型的并行脚本，也没有产生新的加速比结论。

### 3. 四道护栏分别约束不同风险

| 护栏 | 当前实现 | 不能过度承诺的地方 |
|---|---|---|
| 迭代上限 | MainAgent max_iters=15，Search/Trade 为 6 | 是各 Agent 的迭代次数，不是全请求工具调用总数或总耗时上限 |
| 分级超时与熔断 | ToolResilienceMiddleware 使用 wait_for；按工具名统计失败，支持打开、半开探测与恢复 | 超时取消不代表外部写操作已回滚；预算与业务幂等仍需另行处理 |
| 结果与上下文治理 | ContextConfig 配置工具结果长度上限、压缩触发比例 0.75、保留比例 0.15；结构化 ERROR 让模型感知失败；Harness 可追加提示 | 不同工具的中间件覆盖不同；压缩提示词要求保留事实，不是保真证明 |
| Token 预算 | build_agent_middlewares() 在 REPLY_TOKEN_BUDGET>0 时添加 ReplyBudgetControlMiddleware；另有请求级 TokenBudget | 两项配置默认均为 0，不能声称默认都已启用；作用范围也不同 |

当前工具超时默认值包括商品搜索 90 秒、品类知识 15 秒、订单操作 10 秒、派发 180 秒，未列出的工具使用 30 秒。进程内 CircuitBreakerRegistry 默认连续失败阈值为 3、冷却 60 秒；中间件也支持异步共享注册表。按工具名共享故障视图意味着不同会话可以共同触发熔断，这是与 LoopDetector 按会话隔离不同的设计。

Token 预算还有一个容易说错的细节：核对当前安装的 AgentScope `middleware/_budget.py`，ReplyBudgetControlMiddleware 累计的是单次 reply 内多步模型调用的加权输入/输出 Token；达到阈值后，在后续推理前注入收尾提示，并将 tool_choice 设为 none。它不是只限制最终答复长度，也不是在阈值处立刻截断当前模型调用。项目自己实现的请求级预算另行承担跨派发累计与降级选择，不能将两者混为一谈。

当前还装配了 `CriticalFactsMiddleware`，将部分结构化事实保存在 AgentState.middle_context；这比只依靠摘要提示词更具体，但仍应按其字段提取范围验证，不能宣称所有事实都不会丢失。

### 4. 精确白名单与规则去重，不等于业务确认和操作幂等

`permissions.py` 对已知订单写工具、Task 工具、派发及偏好工具追加 ALLOW 规则，没有通过该函数设置全局 BYPASS。MainAgent 和 TradeAgent 构建时会应用这些规则。其意图是避免对话层确认后再次被工具权限确认挂起，并让未列入白名单的新工具继续走框架权限判断。

追加规则前，代码检查该工具是否已有 source 为 projectSettings 的规则，已有则跳过。这避免恢复 AgentState 后反复追加同源规则；它不是重新校验旧规则一定与最新配置完全一致，更不是创建订单的业务幂等机制。

对话层的“先出确认卡，买家明确确认后再执行”写在 `globex.yml` 中。白名单本身不验证是否已有确认卡或有效用户确认，不能把它描述为服务端强制确认校验。未使用全局 BYPASS 也只说明未全面绕过权限引擎，具体新工具能否运行仍需结合其属性和权限上下文判断。

还需注意配置同步：当前 product_search_tool 已在 SearchAgentFactory 中标记为非只读，但不在 `_AUTO_ALLOWED_TOOLS` 中；SearchAgent 构建也没有调用 allow_business_tools。是否出现额外确认应在真实权限流程中验证，不能沿用“所有搜索都是只读、肯定直接放行”的旧假设。本次仅记录这一静态配置风险，未复现权限挂起。

### 5. 主 Agent 保留会话，子 Agent 隔离临时上下文

`SessionRegistry` 按 shopping_session_id 缓存主 Agent；进程内再次请求该会话时复用已有实例，首次访问则先尝试恢复快照。它有助于保留历史对话和任务状态。

`task_dispatch()` 每次调用 Search/Trade 工厂新建子 Agent，不传入主 Agent 的 AgentState，主要通过 demands 提供任务信息；搜索子 Agent 还可以由服务端按买家身份加载并选择偏好注入。因此独立上下文不等于“完全没有买家信息”，也不等于进程或数据隔离：仓储、模型网关限流器、事件总线等依赖仍可共享。

这种生命周期分工减少了子任务中间消息直接进入主对话的数量，代价是需要明确传递关键条件，且会重复创建推理上下文。当前注册表的 `_agents` 字典没有在这个类中实现容量淘汰，也没有锁住首次创建过程；不能仅凭按 session_id 缓存就声称解决了会话内并发互斥、多进程一致性或长期内存增长问题。

### 6. 快照失败降级保证局部可用，不保证全系统绝不失败

`SessionRegistry.persist()` 将 `agent.state.model_dump_json()` 交给 SessionStore 保存，并捕获保存异常记录 warning。文件实现写入 JSON 文件，SQL 实现保存状态字符串。“一行落盘”是对序列化调用简洁的概括，实际还依赖存储读写和恢复策略。

恢复路径明确处理三种情况：存储读取异常时告警并返回 None；快照不存在时直接返回 None；JSON/AgentState 校验异常时告警并返回 None。工厂据此创建新状态。这使恢复失败不必阻断后续对话，但旧的上下文、计划或待确认信息可能丢失，不能把可继续服务描述为无损恢复。

截图中的“绝不 500”应收紧为“这些读取和反序列化异常在注册表内被捕获”。Agent 构建、其他依赖或接口本身仍可能失败，当前函数不提供全链路绝不报错的保证。文件 SessionStore 使用直接 write_text，也不能由 model_dump_json() 推导出原子写入或崩溃一致性。

### 可直接讲述的面试版本

这个项目的难点不只是把主 Agent 和子 Agent 连起来，而是让编排方式、资源限制和状态生命周期配合起来。主 Agent 自己就有业务工具，简单任务直接执行；需要独立并行或者隔离大量中间信息时，再派发新的子 Agent。主 Agent 按会话复用，子 Agent 每次派发新建，保留长期对话与隔离临时过程分别处理。

并行方面，框架支持并发工具批次，提示词要求独立任务同轮派发，但这两个条件不能代替实测。项目提供脚本同时观察总耗时与派发时间区间，避免把模型说“我会并行”当成真的并行；正式比较还要确认两次任务量和结果质量一致。

可靠性方面，分别设置迭代上限、工具超时与熔断、上下文治理，以及可选 Token 预算。会话快照读取或解析失败时可以按新会话继续，代价是可能丢上下文。权限上只对白名单工具追加规则，并防止恢复后重复追加；但规则去重不是订单幂等，提示词里的确认要求也不能冒充服务端确认校验。

我的核心认识是，每个机制都要说清作用范围和实际接入：提示词负责引导选择，代码负责执行约束，运行轨迹负责验证行为。比如能并发不代表每次都并发，状态可恢复不代表无损恢复，有护栏实现也不代表每个工具都已覆盖。

## 延伸案例：刷新后页面空白，如何区分数据丢失与恢复链路缺失

核对日期：2026-09-17。截图提供了合理的排查思路与验收目标，但其服务端会话目录、Skill/收藏恢复、运行续读和停止功能不能直接视为当前工程已实现。本节依据当前 frontend/src/App.tsx、服务端路由、存储和事件总线区分现状与目标。

### 当前代码实际会发生什么

前端 `loadOrCreate()` 将 `globex.session` 和 `globex.buyer` 两个 ID 写入 localStorage。`turns`、`events`、`streaming` 则初始化为 React 内存状态，未持久化。商品卡组件从 events 中取最近商品结果。因此普通刷新即使保留了同一买家和会话 ID，历史消息与商品卡仍会从空状态开始。

页面初始化只重新订阅 WebSocket，没有请求历史会话或消息。后端保存 AgentState 的能力，是在后续处理意图时为 Agent 恢复推理上下文，不能自动替前端恢复消息列表。这是“后端有状态”和“用户能看到历史”之间的具体差别。

清空 localStorage 后，当前代码会重新随机生成买家 ID 和会话 ID。旧数据可能仍在原作用域内，但前端已换了身份和指针。源码没有读取 `VITE_BUYER_ID`，所以仅按截图设置该变量不会固定当前页面的买家身份。

### 排查顺序：先确认身份和数据源，再找丢失环节

1. **核对 buyerId 与 sessionId。** 查看页面头部显示的两个 ID 与实际请求体，对照刷新或故障前记录。先不要清缓存、造新 ID 或清库，否则会改变排查条件。
2. **核对请求实际发往哪里。** 当前前端使用 `VITE_API_BASE`，默认 http://127.0.0.1:8000；Vite 配置没有后端代理。切换前端端口会改变浏览器 localStorage 的来源作用域，从而可能产生新 ID，但不会自动更换这个默认 API 地址。以浏览器请求 URL 为准，不能只看启动终端。
3. **核对真实存储配置。** `DATABASE_URL` 显式配置优先；未配置时默认 SQLite 位于 DATA_DIR/globex.db；DATABASE_URL=file 则走文件存储。只查 DATA_DIR 不足以确定会话和偏好存在哪个数据库，商品与推荐缓存又可能仍在 DATA_DIR 中。检查时不应输出数据库密码或整份环境文件。
4. **按相同 sessionId 检查服务端证据。** SQL 模式可分别核对 conversation_sessions、conversation_messages、conversation_events、agent_session_states；文件模式核对对应会话快照和流水。现有路由未暴露买家会话目录与详情接口，因此截图中“查目录与详情”目前需通过存储层或只读数据库检查，不能假装已有该 HTTP 接口。
5. **定位写入、读回还是渲染。** 有记录而页面空白，在当前版本首先符合“未实现历史读回”的代码现状；若未来接口已返回内容但页面仍空白，再查初始化和渲染。库中无记录时，还需区分任务未结束、存储配置不一致、写入失败或异常退出，不能直接认定数据被删。

`_record_conversation()` 在本轮收尾阶段写会话、买家消息、Agent 消息与事件；token.delta 明确不入库。各存储调用并非整个对话轮次的统一事务，写入失败只记录 warning，因此可能出现目录有记录、消息或事件不完整的部分写入。运行中的“暂时无历史记录”也不一定是保存失败。查问题时要同时看任务状态、写入时机与日志。

### 断线重连不等于断点续读

前端 WebSocket 断线后每 1.5 秒尝试重连，并以相同 sessionId 重新订阅。事件总线 `subscribe()` 创建新队列，没有读取持久化事件、事件游标或补发历史。因而重连可接收后续事件，但断线期间的 token 或最终结果可能已错过。

提交意图时，前端调用同步 `POST /commerce/intents`，没有解析返回 JSON，也未检查 response.ok。最终回复主要依赖 WS 的 final.result 写入页面。即使 POST 正常返回 final_text，只要 final.result 在断线时丢失，页面也可能拿不到最终回复；HTTP 4xx/5xx 也不一定触发 fetch 的异常分支。这些是代码可推导的缺口，本次没有进行浏览器故障注入。

后端另有异步提交接口与 `GET /commerce/tasks/{task_id}`，在队列启用时可查询任务状态，但当前页面未使用它们，也不保存 task_id。不能把“有任务查询 API”说成“页面已经支持刷新后续读同一个 run”。当前自动重连确实没有重新 POST 意图，但也没有完整恢复运行状态。

### 截图验收项与当前实现逐项对照

| 截图中的操作 | 当前代码能确认的情况 | 后续验收目标 |
|---|---|---|
| 普通刷新 | ID 保留，消息和商品事件状态重新置空，无历史加载 | 按身份与会话从服务端恢复可展示记录 |
| 清 localStorage 后再打开 | 重新生成买家与会话 ID，无服务端最近会话查找 | 先建立稳定身份，再恢复该买家的会话目录；浏览器只保存可丢失的定位信息 |
| 设置无效会话指针 | 非空字符串直接采用，无有效性/归属校验与回退 | 校验会话存在且属于当前买家，再选择有效历史会话 |
| 主动新建选购 | 当前页面没有新建会话入口 | 区分主动新建和指针失效，主动新建不得被最近会话回退覆盖 |
| 运行中断线重连 | 仅重新订阅未来 WS 事件，没有事件补发与 task_id 续查 | 续查同一个任务并补齐已保存结果，避免恢复动作重复提交意图 |
| 点击停止再刷新 | 当前页面没有停止按钮和运行取消恢复流程；取消订单不是停止 Agent 运行 | 持久化运行取消状态，明确保留范围及副作用结果 |
| 待确认时刷新或 API 重启后读回 | 有 AgentState 快照，但没有前端确认状态重建与完整审批恢复流程 | 明确展示待确认/中断状态，不把丢失状态推断为已批准 |
| 切换买家 | 偏好存储按 buyerId 分隔，但会话与订阅主要依赖 sessionId | 校验会话、任务、订单的身份归属，并清理不属于当前买家的界面状态 |

截图提到的 Skill 保存、收藏和 pao-coder 示例，在当前页面及服务端路由中没有找到对应完整业务流程。当前偏好记忆不能直接等同于用户 Skill 或收藏系统，不能将截图全部步骤写成已通过的项目验收。

### 买家字段分桶，不等于身份与访问隔离

当前 SessionRegistry 和 AgentSessionStateRow 以 sessionId 为键，WS 订阅只提交 sessionId；会话 touch_session() 发现同名会话时只更新时间，没有验证原 buyerId 与本次是否一致。订单查询和取消路由也没有在其入口接收并核验买家归属。

所以“换买家不会继承其他人的会话和订单”不能由偏好存储的隔离测试推导出来。恢复功能需要绑定可信身份并校验资源归属，前端传入一个 buyerId 不是身份认证。此处是静态代码发现的隔离缺口，本次未尝试跨买家访问真实数据。

### 备份与验证应保留原始证据

当前 SQLite 连接明确开启 journal_mode=WAL。截图提醒不要在运行中只复制主数据库文件，应作为备份操作边界记录：可在停止所有相关写入进程后复制实际数据目录及目录外的数据库文件，或使用 SQLite 一致性备份机制；不能把一份随手复制的主文件当成已证明完整的备份。当前检查范围内未找到配套备份脚本，本次也没有操作数据库备份或清理。

隔离验证环境应明确设置后端端口、DATA_DIR 和 DATABASE_URL，并把 VITE_API_BASE 指向该后端。截图中的 VITE_BUYER_ID 与代理方案要先有对应实现才能采用。验证前记录买家、会话、数据库位置及预期消息/商品，逐项操作后同时核对服务端记录与页面表现，不能只看页面是否“像恢复了”。

### 可直接讲述的面试版本

项目里一个容易混淆的问题是“刷新后内容没了”。这不一定代表数据库丢数据。我会先核对买家身份、会话 ID、后端地址和实际数据库位置，再区分是没有写进去、没有读回来，还是读回来没有渲染。

根据当前代码，前端只把买家和会话 ID 放在 localStorage，消息和商品卡都在 React 内存里，刷新时又没有从服务端加载历史。后端虽然保存了 AgentState 和对话流水，但那还没有形成用户界面的恢复链路。清缓存还会生成新买家 ID，所以不能用反复清缓存或随机换 ID 来掩盖问题。

另一个缺口是 WebSocket 能重连，但不会补发断线期间的事件；前端也没有消费同步请求返回的最终文本，所以结果可能已生成，页面仍然缺失。后续应先补稳定身份、带归属校验的会话读回和任务续查，再做刷新、断线、无效会话指针和主动新建等验收。当前完成的是问题定位与方案整理，还不能说完整恢复已经实现。

| max-num-seqs | GPU 利用率 | 单请求 P99 | 吞吐量 |
|---:|---:|---:|---:|
| 1 | 18% | 2.1 s | 0.5 req/s |

速记重点：16 对应 78%、2.8 秒、5.5 req/s；32 对应 85%、3.8 秒、7 req/s。16 → 32 时，吞吐增加约 27%，P99 增加约 36%。在这些截图数据中，若目标为 P99 不超过 3 秒，16 比 32 更符合目标；这只是该组数据下的取舍，不能认定所有部署的最优并发都是 16。

### 预热应该如何实施

以下是结合截图整理的实施方案，不是当前仓库已经完成的脚本：

1. 启动推理服务，等待模型引擎就绪并完成启动期初始化。vLLM 本身可能在启动阶段执行编译和 CUDA graph 捕获/预热，具体依版本与配置；不要将这些全部说成第一次 HTTP 请求才发生。[vLLM GPU worker 实现](https://docs.vllm.ai/en/latest/api/vllm/v1/worker/gpu_worker/)
2. 在对外放流量前，向推理端点发送约 50–100 条合成请求，覆盖代表性的 system prompt、工具 schema、短长输入与一定长度的输出；从小并发逐步增加至目标并发，而不是同时灌入 100 条。
3. 分别覆盖 LLM 和 reranker 的实际输入形态，例如 reranker 使用代表性的 Top-100 候选。仅测健康接口或一句极短问候，不能代表真实工作负载已预热。
4. 预热使用只读/模拟工具或直接推理端点，不执行真实下单、取消或偏好写入。避免业务语义缓存直接返回结果导致请求根本没到模型；区分重复前缀缓存收益与不同输入下的稳态表现。
5. 确认请求成功、延迟与资源状态稳定后，再通过应用或负载均衡层的流量准入开关接收真实请求。50–100 条是材料里的经验数量，不是达到条数就必然就绪。
6. 另行采集足够的冷/热测试样本，用一致的模型、输入输出长度和并发条件比较。vLLM 提供 /metrics 供监测，具体指标应以部署版本为准。[vLLM 监控文档](https://github.com/vllm-project/vllm/blob/main/docs/usage/metrics.md)

当前 `Container.startup()` 做的是建表、创建队列消费者组、商品向量索引与知识库初始化；本次检索未发现启动后发送 50–100 条 LLM/reranker 预热请求或预热完成后放流量的逻辑。建索引可能调用 embedding，但不等于完整推理服务预热。故回答“项目现在怎么做冷启动”时，应如实说当前有依赖初始化，截图中的模型预热流程仍待实现。

### 截图总结中的其他边界

本次材料明确其“三板斧”为 max-num-seqs=16、FP16、continuous batching，补充了前节未给出的组成。A100 单卡 2→16 并发、35B 总参数/14B 激活参数也按材料记录，具体模型和部署未核实。MoE 每 token 激活参数较少不等于只需存储这些权重，不能仅凭“14B 激活”推出单卡必然装得下。LLM 与 reranker 分卡是材料推荐的资源隔离选择，不是所有配置共卡必然 OOM。
